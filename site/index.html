1.0 · SSH and SFTP

Nobody keeps a key to your servers.

postern is an SSH bastion that mints a short-lived certificate per session and records what happens. Targets hold no authorized_keys, users land as themselves, and a session that cannot be recorded does not start.

One connection, four decisions

Everything postern does happens between ssh and your server.

# the user types this — no client, no agent, no plugin
$ ssh yigit:web-01@bastion
  • Who are you. A local credential, your directory, or your identity provider. An OIDC identity is bound by (iss, sub) — never by a username somebody can edit.
  • What may you reach. Roles, resolved live at connect time, so a revoked grant does not wait for a session to end. No role, no answer.
  • How do you get in. A fresh ed25519 key is generated for this one session, signed by postern's CA for a single principal, and valid for five minutes — long enough to finish a handshake, not long enough to be worth stealing. It never touches disk, it carries permit-pty and nothing else, and the target never holds a key of yours.
  • What happened. The session is recorded as asciicast v2 and replays in the panel or with asciinema play. If the recording cannot be written, the session is refused.

Refusals are the feature

Most of postern is a list of things it declines to do, each with a reason.

Only accountable requests cross

Agent forwarding and X11 are refused: both open a second channel around the bastion. Unknown request types are refused too — default deny, so tomorrow's SSH extension does not slip through.

SFTP is read, not waved through

File transfer is off by default. Switched on, every open, transfer, rename and delete is recorded per file — with the bytes that actually crossed, and refusals kept as refusals.

Host keys are pinned

Every target's key is stored and checked. InsecureIgnoreHostKey appears nowhere in the source. A target that presents a different key is reported, not accepted.

"Empty" is not "unknown"

A directory that answers with no groups and a directory that cannot be reached are different facts, and postern keeps them apart. An outage never reads as "this user lost access".

A second key needs a second proof

Adding a further SSH key is how someone keeps a stolen account, so it asks again — a password, or a code from an authenticator you enrol yourself. Directory users are not sent to an administrator.

The way back in stays open

A break-glass administrator lives on the host, not in your identity provider. Switching the panel to SSO leaves it in place, so an IdP outage is not a lockout.

What it isn't

1.0 is deliberately narrow. If you need something below, postern is the wrong tool today and probably tomorrow.

Not in this release

  • SSH and SFTP only. No HTTP, RDP, VNC, MySQL, PostgreSQL or Kubernetes proxying.
  • One node. No clustering, no shared state between instances, no S3 offload — recordings are files on the bastion's disk.
  • No port forwarding. direct-tcpip is refused; a tunnel postern cannot record is a tunnel it will not carry.
  • TOTP only for the second factor — no WebAuthn, no push.
  • No agent on the target. That is the point, and it is also the limit: postern sees the SSH channel, not the processes behind it.

It is also new. The proxy, certificates, recording, RBAC, the panel, OIDC and LDAP are exercised against real OpenSSH, Keycloak and OpenLDAP on every change — but 1.0 means "we think this is right", not "this has run in twenty companies for three years".

What an operator actually holds

PieceWhat it is
The bastionOne Go binary. The panel is compiled into it; there is no second service to run.
StatePostgreSQL. Users, roles, targets, sessions, audit — all of it, in schema you can read.
RecordingsPlain asciicast files on disk, one per session, pruned on a retention you set.
On each targetOne line of sshd_config trusting postern's CA. No daemon, no package.

Nine Go modules at runtime, four in the panel. Nothing is pulled in that could be written in an afternoon and tested in a morning — the TOTP, QR and SFTP-audit code is postern's own, checked against the RFC test vectors and a reference encoder.

Fifteen minutes, honestly

# 1. keys and schema
$ postern ca init --key /etc/postern/ca_ed25519
$ postern db migrate

# 2. the way back in — the secret is printed once
$ postern admin bootstrap

# 3. one line on every target
TrustedUserCAKeys /etc/ssh/postern_ca.pub

# 4. connect
$ ssh you:web-01@bastion

Step 3 is the only thing that touches your servers, and an Ansible role does it: it validates with sshd -t before installing and reloads rather than restarts, so nobody's session dies for it.
