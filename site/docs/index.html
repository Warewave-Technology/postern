How it works

A user connects to postern, not to the server. postern authenticates them, decides whether they may reach the target they asked for, mints an SSH certificate for that one session, opens the connection on their behalf, and records it. 

user                      postern                     target
 |                          |                            |
 |-- ssh yigit:web-01@ --->|                            |
 |                          |-- who are you?             |
 |                          |   (local / LDAP / OIDC)    |
 |                          |-- may you reach web-01?    |
 |                          |   (roles, resolved now)    |
 |                          |-- mint cert, principal yigit|
 |                          |   valid minutes, in memory |
 |                          |---- ssh with cert ------->|
 |<===== session, recorded to asciicast =====>|

The target never holds a key belonging to the user. Removing someone's access is a change in postern, not a sweep across a fleet of authorized_keys files.

What the certificate actually says

A fresh ed25519 key pair is generated per session, in memory. The certificate over it:

FieldValue
Validityfive minutes, with a small backdate for clock skew
Principalsexactly one — the user's os_user
Extensionspermit-pty, and nothing else
Serialrandom, 64-bit
Key IDidentifies the session in the audit trail

The missing extensions are the interesting part: no permit-agent-forwarding, no permit-port-forwarding, no permit-X11-forwarding. Even if postern's own refusals were bypassed, the target's sshd would still decline them.

Five minutes is enough to complete a handshake; the session then runs as long as your session limits allow. A certificate captured off the wire is worth nothing shortly after it is issued.

Clock skew

postern refuses to sign if the host clock is before 1970 rather than emitting a certificate that wraps into "never valid" — which surfaces on the target as certificate is not yet valid and sends you looking in the wrong place entirely. Keep NTP running: a bastion with a wrong clock issues certificates nothing will accept.

The username carries the destination

There is no client, plugin or agent. The routing lives in the SSH username, split by : — <login>:<target>. 

$ ssh yigit:web-01@bastion          # login as yigit, go to web-01
$ ssh -J bastion ...                # not this; postern is not a jump host

The Linux account you land in is the user's os_user, held in postern. It defaults to their username and an administrator can change it; the certificate's principal is that value, so a target's AuthorizedPrincipalsFile stays the final say.

Install

1. Get a binary

Either download a release, or build from source. Releases carry a single static binary per platform with the panel already compiled in. 

$ curl -LO https://github.com/warewave/postern/releases/download/v1.0.0/postern_1.0.0_linux_amd64.tar.gz
$ curl -LO https://github.com/warewave/postern/releases/download/v1.0.0/checksums.txt
$ sha256sum -c checksums.txt --ignore-missing

The checksums file is signed, and there is no public key to look after: the signature is bound to the repository and the workflow that produced it. With cosign installed: 

$ curl -LO https://github.com/warewave/postern/releases/download/v1.0.0/checksums.txt.sig
$ curl -LO https://github.com/warewave/postern/releases/download/v1.0.0/checksums.txt.pem
$ cosign verify-blob checksums.txt \
    --signature checksums.txt.sig --certificate checksums.txt.pem \
    --certificate-identity-regexp '^https://github\.com/warewave/postern/\.github/workflows/release\.yml@' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com
Ask a binary what it is

postern version prints the tag it was built from, the commit, and whether that commit's tree was clean. A build that did not come from a release tag says so rather than inventing a number, and a binary built from a modified tree is marked MODIFIED — which is the distinction that matters when you are checking whether a patch is really in the thing you are running. go version -m ./postern lists the dependency versions it was compiled with.

1b. Or build from source

$ git clone https://github.com/warewave/postern && cd postern
$ make build          # embeds the panel bundle that is committed to the repo
Note

The panel is compiled into the binary with go:embed, from web/dist — which is committed, so a fresh clone builds the right panel without Node installed. make build does not rebuild it. If you change anything under web/src, run make web first: without it the binary silently embeds the previous bundle, and nothing warns you. CI catches a bundle that has drifted from its source, which is the only reason the committed copy can be trusted.

Rebuilding the web assets alone does not change a running server either — you need a new binary.

2. Database

CREATE ROLE postern LOGIN PASSWORD 'choose-one';
CREATE DATABASE postern OWNER postern;

Put the connection string in the config, or keep the password out of the file with POSTERN_DATABASE_DSN, which overrides database.dsn when set.

sslmode

If your DSN names no sslmode, postern uses verify-full. libpq's own default silently falls back to plaintext when TLS is unavailable — not a trade a bastion should make on your behalf. Set sslmode=disable explicitly if the database is on the same host and you mean it.

3. Keys and schema

$ postern ca init --key /etc/postern/ca_ed25519      # prints the CA public key
$ ssh-keygen -t ed25519 -N '' -f /etc/postern/host_ed25519
$ postern secret init --config postern.yaml          # seals stored settings
$ postern db migrate --config postern.yaml
Back these up now

The CA private key and the secret key are not recoverable. Lose the CA and every target must be re-trusted; lose the secret key and stored LDAP/OIDC credentials cannot be decrypted. § Backup.

4. The way back in

$ postern admin bootstrap --config postern.yaml
administrator: admin
sign-in secret: XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX   # shown once

The secret is generated by the host and printed once. It is never a password somebody chose, and it is never shown again — reissue with postern admin issue if it is lost.

5. Start

$ postern serve --config postern.yaml

deploy/systemd/ in the repository runs it as a service.

Your first connection

  1. Open the panel and sign in with the bootstrap secret. An unconfigured bastion shows first-run setup and nothing else.
  2. Register a target (§ Targets) and trust the CA on it (§ Trusting the CA).
  3. Create a role, grant it the target, give it to a user.
  4. Add your public key under Profile → SSH keys, then connect.
$ postern role add --name ops --target web-01 --config postern.yaml
$ postern user add --name yigit --os-user yigit --role ops \
      --key ~/.ssh/id_ed25519.pub --config postern.yaml
$ ssh yigit:web-01@bastion -p 2222

The panel

The panel is served by the same binary — no second service. Users see their own targets, their own sessions, and their own profile; administrators additionally see users, roles, targets, mappings, sync and every session. 

http:
  addr: "127.0.0.1:8088"
  external_url: "https://bastion.example.com"   # what the browser reaches
  trusted_proxies: ["10.0.0.9"]                 # your TLS terminator
  terminal_enabled: false                       # see below

external_url is not decorative and cannot be derived from addr: sign-in links and the OIDC redirect_url are built from it, and a bastion behind a proxy or NAT has no idea what :8088 means to the outside world.

The browser terminal is off by default

With terminal_enabled on, the shell button on a target opens a session inside the panel. That is genuinely convenient, and it changes what a cross-site scripting bug in the panel is worth: with the terminal off, an XSS can call the API; with it on, the same XSS can run commands on your servers.

So it is opt-in. An installation that does not need it should not carry the surface — the code existing is not a reason for the door to be open. The same menu copies the ssh command for a real terminal, which most operators end up preferring anyway.

If you turn it on

Serve the panel over HTTPS (an https:// external_url) and keep it behind the reverse proxy. postern already sends a strict CSP and checks Origin on the WebSocket upgrade; those defences assume the transport is not plaintext.

Tell postern about your reverse proxy

postern rate-limits sign-in attempts per (account, source address), so one attacker can only slow themselves down. Behind a proxy, every request arrives from the proxy's address and that pair collapses to the account alone — at which point an unauthenticated stranger can keep your administrator waiting at the door indefinitely, one request every five minutes, without needing to guess anything (admin is the default name).

trusted_proxies fixes it. List the addresses your proxy actually connects from; only for those does postern read X-Forwarded-For, and it walks the chain from the right so a client cannot claim someone else's quota by prepending an address. 

http:
  trusted_proxies: ["10.0.0.9", "10.1.0.0/24"]
List the proxy, not the network

Empty is the default and means the header is never read — correct for a directly exposed bastion, because otherwise any client could pick its own rate-limit bucket. Listing a broad range hands that choice to everyone inside it. A malformed entry stops startup rather than leaving you thinking you configured something you didn't.

It is an audit setting too, not only a rate-limit one

A browser terminal session records its source address the same way, so without trusted_proxies every panel-opened session is filed under the proxy's address and two people behind it cannot be told apart afterwards — in the audit list, on the target page, in the SFTP file history, and in the log line written when someone closes a session. SSH sessions in that same column always carry the real client address, which is what makes the mismatch easy to miss. The flip side is that a range listed here is a range whose members can choose what a permanent audit row says about them.

Put TLS in front of it either way

postern serves the panel over plain HTTP. Terminate TLS at a reverse proxy, or bind addr to localhost and reach it over an SSH tunnel. Session cookies are HttpOnly and SameSite, but a plaintext hop is a plaintext hop.

Registering a target

$ ssh-keyscan -p 22 10.0.0.11 > web-01.pub    # look at it before trusting it
$ postern target add --name web-01 --host 10.0.0.11 --port 22 \
      --host-key-file web-01.pub --grant-role ops --config postern.yaml
$ postern target list --config postern.yaml

--host-key-file is required. postern will not register a target whose host key it was not given, and from then on that key is pinned: a target presenting a different one is reported, never silently accepted. InsecureIgnoreHostKey appears nowhere in the source.

The panel offers to fetch the key for you, and is careful about what that means: the fetched key is shown as a fingerprint for you to compare against the machine itself, and nothing is stored until you say you compared it. If the same address is already registered under a different key, it says so — and it distinguishes a different key from a different key type, because giving a real alarm the same voice as a common, innocent situation is how alarms stop working.

This is still trust on first use

Pasting the output of ssh-keyscan was always TOFU too — usually run from the same network. The fetch removes the typo and the temptation to leave the field blank; it does not remove your obligation to check the fingerprint on the console of the machine.

Trusting the CA

This is the only change postern needs on your servers.

# /etc/ssh/sshd_config
TrustedUserCAKeys /etc/ssh/postern_ca.pub
AuthorizedPrincipalsFile /etc/ssh/auth_principals/%u

# /etc/ssh/auth_principals/yigit
yigit

Print the key to install with:

$ postern ca show --key /etc/postern/ca_ed25519

Across a fleet

deploy/ansible/ does it. The role validates the resulting configuration with sshd -t before installing it, and reloads rather than restarts.

Why that matters

An invalid sshd_config takes the host away at its next restart, and you cannot SSH in to fix it. Never install one unvalidated — and keep a second way into a new target until you have proved certificate login works on it.

$ ansible-playbook -i inventory.ini deploy/ansible/example/targets.yml

Proving it works

$ ssh -v yigit:web-01@bastion -p 2222
# on the target, if it does not:
$ journalctl -u ssh -n 50

test/integration/testdata/certtarget/Dockerfile is the same setup as a runnable file, and is what the certificate tests run against.

Discovery

If your machines live on Proxmox or vSphere, postern can read them from the hypervisor and turn a tag into a role grant. Without --apply it only prints what it would do. 

$ postern discover proxmox \
    --url https://pve.example.com:8006 \
    --token-id 'postern@pve!discovery' \
    --token-secret "$PVE_TOKEN" \
    --tag-key role \
    --config postern.yaml

Proxmox tags are flat strings, so the key and value share one tag. The separator may be =, : or _, with or without spaces — and because Proxmox itself only permits [a-z0-9_.+-], in practice you will write role_os-admins.

TagWith --tag-key role
role_os-adminsgrants to role os-admins
role=opsgrants to role ops (vSphere, where = is legal)
productionno key, so it names no role — the machine lands in unknown

vSphere carries real tag categories, so --tag-key names the category: 

$ postern discover vsphere --url https://vcenter.example.com \
    --username 'discovery@vsphere.local' --password "$VC_PASS" \
    --tag-key role --config postern.yaml
Read-only, and dry by default

Use a credential with read permission only, and nothing is written without --apply.

The exit code answers a narrower question than you might expect. An --apply exits non-zero only when machines were found and nothing at all was written — no target, no role, no grant. It does not key on your --tag-key matching: a run where most machines carry no role tag still creates targets, puts them in unknown, and exits zero. A discovery that finds no machines at all also exits zero. So a typo in --tag-key is visible in the summary — every machine in unknown — rather than in the exit status.

Labels

Labels are free-form key=value pairs on a target, used to group and filter in the panel. 

$ postern target label set --target web-01 --key env --value prod --config postern.yaml
$ postern target label remove --target web-01 --key env --config postern.yaml

Labels describe; they do not grant. Access comes only from roles.

Users and roles

A role is a named set of targets. A user's access is the union of their roles, resolved at connect time — so revoking a role takes effect on the next connection, not at the end of the working day. 

$ postern role add --name ops --target web-01 --target web-02 --config postern.yaml
$ postern user add --name suleyman --os-user suleyman --role ops --config postern.yaml
$ postern user list --config postern.yaml
$ postern user modify --name suleyman --os-user deploy --config postern.yaml

Changing someone's roles

$ postern role list --config postern.yaml
$ postern user grant-role  --name suleyman --role ops --config postern.yaml
$ postern user revoke-role --name suleyman --role ops --config postern.yaml
$ postern role revoke-target --name ops --target web-01 --config postern.yaml

Three things these say out loud, because each is a way you would otherwise be misled:

  • Revoking a role the user never held reports held no active grant, not revoked — a mistyped role name should not read as success.
  • Revoking a role that came from a directory group lasts until that person's next sign-in; removing the group mapping is what makes it stick.
  • Granting a role they already have from a directory group turns it into a manual grant that synchronisation can no longer take away — so it survives them leaving the group. Not blocked, but said.
Break-glass never blocks

Granting a role to a deleted account is allowed — restoring roles before reactivating is a legitimate order — and the command tells you the account cannot sign in yet. The CLI is the path that has to work when the panel does not; refusing a legitimate ordering is how that promise gets broken.

Leaving

Accounts are not deleted out from under the audit trail. An account moves through states, and a departed one keeps its record: 

$ postern user state --name suleyman --set deleted --config postern.yaml
$ postern user purge --name suleyman --config postern.yaml   # frees the username,
                                                             # keeps that it existed
StateMeaning
activemay sign in and connect
inactivethe directory stopped confirming them; no access, record intact
deletedgone, but their sessions still have an owner

Where identities come from

SourceUse
localSmall teams and the break-glass administrator. Host-issued secrets, argon2id.
LDAP / ADUsers and groups read from the directory; group membership becomes roles.
OIDCSign-in at your IdP; groups from a claim become roles.

Configure through first-run setup in the panel, or with the CLI:

$ postern settings set --key auth.source --value ldap --config postern.yaml
$ postern settings set --key ldap.url --value ldaps://dc.example.com --config postern.yaml
$ postern settings set --key ldap.bind_password --secret --config postern.yaml
                                                # value left blank: asked for
                                                # at the terminal, stored sealed
$ postern settings test-ldap --config postern.yaml     # before you rely on it
$ postern settings list --config postern.yaml          # secrets masked

Identity is bound by (iss, sub)

An OIDC user is bound to your postern account by the issuer and the subject — stable, opaque values. Not by preferred_username, which people rename and administrators reassign. Renaming somebody in the IdP does not hand them another person's access.

First binding is confirmed out of band: postern shows a code in the browser that must be matched in the terminal, so a stolen browser session alone cannot attach an identity to an account.

Just-in-time accounts

With auth.auto_create on, a user whose group maps to a role gets an account on first sign-in. With it off, they are written to a pending queue for an administrator to approve — keyed by their stable identity, so renaming does not let anyone apply twice. Either way, a user with no mapped group is refused and no account appears.

Group mappings

$ postern mapping add --group sysadmins --role ops --config postern.yaml
$ postern mapping list --config postern.yaml
$ postern mapping unmapped --config postern.yaml   # groups seen at login
                                                   # with no role behind them

unmapped is the diagnostic to reach for when somebody says "I signed in but I can't see anything": their group arrived and nothing was waiting for it.

Large AD groups

Active Directory returns big groups in slices (member;range=0-1499) and may answer with referrals. postern follows both, up to a bound. When it stops early the result is marked truncated rather than presented as the whole group — an incomplete answer is never rendered as an empty one.

Directory sync

Sync reconciles postern with the directory on a schedule: accounts whose source stops confirming them go quiet instead of vanishing. 

$ postern sync run --dry-run --config postern.yaml   # report, write nothing
$ postern sync run --config postern.yaml
$ postern sync status --config postern.yaml

The brakes exist because a half-answering directory is more dangerous than a silent one:

SettingDefaultStops
sync.max_zero_fraction0.10a run where too many groups came back empty
sync.min_zero_floor3the same, on small installations
sync.max_unknown_fraction0.25a run where too much could not be resolved
sync.max_revoke_per_run25a run that would revoke a fleet's worth of access at once
sync.grace—how long a user missing from the directory waits before their directory roles are revoked. It does not deactivate accounts: that is a separate loop with its own timer (auth.confirm_ttl), and it leaves roles alone and closes the door instead.
sync.dry_runfalseeverything; reports what it would do
Turn it on dry first

Run with sync.dry_run for a cycle and read sync status. A directory filter that is subtly wrong looks identical to a directory that lost people.

Second factor

Users enrol an authenticator themselves under Profile → Authenticator: postern shows a QR code and the secret, and enrolment only completes once a correct code proves the app works.

It is RFC 6238 TOTP — SHA-1, six digits, thirty seconds, one step of tolerance either way. A code that has been used cannot be used again, even inside its window.

Its main job is guarding the thing that would otherwise let a stolen session become permanent: adding another SSH key. That asks for a password or a TOTP code, and directory users are not left waiting for an administrator to do it for them.

Break-glass

The bootstrap administrator lives on the bastion's host, not in your identity provider. Switching the panel to LDAP or OIDC does not remove it. An IdP outage is an inconvenience, not a lockout. 

$ postern admin list --config postern.yaml           # who holds a local secret
$ postern admin issue --name admin --config postern.yaml
$ postern admin revoke --name someone --config postern.yaml
Administrator is not a panel button

is_admin comes from the CLI on the host, or from a directory group you nominate. It cannot be granted from inside the panel — a compromised panel session must not be able to promote itself.

To bind an existing SSO identity to the break-glass account, open the door deliberately for one sign-in: 

$ postern user allow-bind --name admin --config postern.yaml

Sessions and replay

$ postern session list --limit 20 --config postern.yaml
$ postern session list --user yigit --config postern.yaml
$ postern session show <session-id> --config postern.yaml
$ asciinema play /var/lib/postern/recordings/<...>.cast

Recordings are asciicast v2 — plain files that replay in the panel or in any asciinema client. Output is always recorded; input is recorded only if you set recording.record_input.

Reading the audit trail

$ postern log --limit 50 --config postern.yaml
$ postern log --actor yigit --config postern.yaml
$ postern log --action session. --config postern.yaml

The panel and the CLI both write to admin_log; this reads it from the host, which is what you need on the day the panel is the broken thing. --action matches a prefix, so user. returns the whole family; the other filters are exact.

A filter that matches nothing says so distinctly from an empty trail — reading "nothing here" as "no records are kept" is the most expensive mistake an audit tool can invite — and truncated output says it was truncated rather than letting the first rows read as all of them.

Health checks

$ curl -fsS http://127.0.0.1:8088/healthz   # the process is up
$ curl -fsS http://127.0.0.1:8088/readyz    # it can do work

The split is a security decision, not a convention. Neither endpoint asks for credentials — that is what a health check is for — so /healthz touches nothing, and /readyz caches its database answer for a second and collapses concurrent probes onto one. Without that, an unauthenticated request would be a lever on your database at whatever rate someone chose.

/readyz answers "not ready" and no more: a database error can carry a DSN fragment or an internal hostname, and the detail belongs in the log rather than in an unauthenticated response. Neither endpoint depends on setup being finished — a bastion nobody has configured yet is still up, and 503 there would have your proxy declare it dead first.

Closing a live session

The panel's Active sessions card offers Close on a session this bastion is actually carrying. Closing drops the connection to the target, tells the person why — the same line is written into the recording, so a later reviewer is not left staring at a transcript that simply stops — and finalises the recording and the audit row. Who closed it is written to the admin log before anything is closed: if that write fails, nothing is closed and you are told so.

Closing is not revoking

The person can reconnect immediately. Access is decided at connect time from roles and account state; closing a session touches neither. If you need them out, remove what grants the access — and remember that on a directory-backed install the directory is the source, so the change has to hold there too.

A row can be open without running: ended_at is empty means "we never recorded an end", which is also what a crash leaves behind. Those rows are shown but not offered — the button appears only where the process confirms traffic is flowing. Startup closes leftovers from an earlier run and says how many, because their recorded duration will read longer than the real one.

No recording, no session

If the recording cannot be opened, the session is refused rather than allowed to proceed unwatched. That is a deliberate audit-first choice: a bastion whose recording silently fails is worse than no bastion, because you believe you have a trail.

Watch the disk. A full disk stops sessions from starting — which is the intended behaviour, and still an outage. See recording.min_free in § Retention.

SFTP audit

File transfer is off by default. Turn it on per installation:

# postern.yaml
session:
  sftp: true

With it on, postern decodes the SFTP protocol as it passes and records a row per file: the operation, the path, and the bytes that actually crossed. Reads, writes, renames, deletes and directory operations are all kept.

  • Failures are kept as failures. A denied open is evidence, not noise.
  • Counts are what crossed, not what was requested — an interrupted transfer is flushed with what it actually moved.
  • Undecodable is not ignorable. If the stream stops making sense, the session is torn down rather than carried blind.

Per-file records appear on the session's page in the panel next to its replay.

Connecting with an sftp client

The sftp command splits its argument on the first :, so the usual login:target@bastion form is read as a remote path and fails with could not resolve hostname. Pass the user separately: 

$ sftp -o "User=yigit:web-01" -P 2222 bastion

scp has the same constraint; rsync -e takes the same -o User=. Graphical clients have a plain username field, so yigit:web-01 goes in it unchanged.

Retention

# postern.yaml
recording:
  dir: /var/lib/postern/recordings
  record_input: false
  retain: 90d
  min_free: 5GB

  idle_timeout: 30m
  max_lifetime: 12h

session.max_lifetimeclose a session no matter how busy

Sending recordings off the bastion

Until this release the audit trail lived only on the machine being audited. Point postern at an S3-compatible bucket and finished recordings are copied there. 

recording:
  archive:
    endpoint: https://minio.internal:9000   # empty = off
    bucket: postern-recordings
    region: us-east-1
    prefix: postern/production
    access_key_id: AKIA...
    secret_key_file: /etc/postern/archive.key   # 0600
  • The network is never on the session path. Recordings are written locally as before and uploaded afterwards, so an object-store outage cannot refuse a session.
  • Upload, verify, mark, then permit deletion. A 200 from PUT is not proof — postern asks the store with a HEAD before recording success, and only that lets the pruner delete the local copy.
  • Nothing unarchived is ever pruned. The cost is honest: a long outage fills the disk and min_free starts refusing sessions. The pruner logs the backlog well before that.
  • Write-only. The panel shows the bucket and key; it does not fetch. A read credential on the bastion would turn one compromise into exfiltration of the whole archive.
PutObject without DeleteObject is not append-only

A PUT to an existing key overwrites it. If the archive must survive someone who owns the bastion, that protection comes from the bucket — versioning, Object Lock in compliance mode with a default retention, and an identity with neither delete nor lock-configuration rights. postern sends no Object Lock headers on purpose: an attacker holding the credential could otherwise set the retention to zero. postern cannot verify your bucket's configuration and does not claim to.

Checking the bucket

$ postern archive check --config postern.yaml

Three parts: what the bucket reported, what could not be determined, and what postern can never determine. The third is the point — it stops the report being read as "checked, therefore safe". It exits non-zero only when the bucket is unusable right now; weak hardening is a warning, since it may be a decision you made.

A misconfiguration detector, not a control

It runs on the bastion with the bastion's credential, so an attacker who owns the machine gets the same answers. Delete permission sits in the "can never determine" column: testing it would need a delete capability postern deliberately does not have, and under a compliance-mode lock it does not matter.

Setting the key from the panel

Settings → Recording archive takes the access key and rotates it without a restart. The endpoint, bucket and prefix stay in the config file.

The destination is deliberately not editable from the panel

A panel session that could move it would redirect every future recording to a bucket it controls — and dropping the stored secret when the destination changes, the mitigation used for LDAP and OIDC, does not help here, because the attacker can enter a fresh key. Same reasoning that keeps is_admin out of the panel: a compromised session must not be able to redirect the audit trail.

If the key comes from the host, the panel says so and refuses to write one — silently shadowing it would be worse than not offering the field. The secret is never read back, not even masked. The Overview shows recordings on disk, how many are waiting to archive, and how old the oldest one is: age is the signal that matters, because a stalled uploader shows as a backlog that stops getting younger rather than one that grows.

No AWS SDK. The signing is standard-library code pinned to AWS's own SigV4 test vectors, so any S3-compatible store works and no vendor dependency is carried. Single PUT only: a recording is about the size of the output it captured, so realistic sessions stay far below the 5 GB limit — and one that does not is kept locally and reported, never silently dropped.

record_input is a privacy decision

Keystroke capture records a password typed into a prompt on the target. Decide it deliberately, tell the people it applies to, and protect the recordings accordingly.

Config reference

The file holds infrastructure only — addresses, paths, limits. Identity, users, roles and targets live in the database, so a config file can be copied between hosts without carrying access with it. 

listen:
  addr: ":2222"
  external_addr: "bastion.example.com:2222"  # what the panel tells users
  max_conns: 200
  max_conns_per_ip: 10
  handshake_timeout: 30s
  max_auth_tries: 6
  max_channels_per_conn: 10
  max_pending_logins: 64

host_key: /etc/postern/host_ed25519
secret_key_file: /etc/postern/secret.key

ca:
  key_file: /etc/postern/ca_ed25519

database:
  dsn: postgres://postern@localhost:5432/postern   # or POSTERN_DATABASE_DSN

http:
  addr: "127.0.0.1:8088"
  external_url: "https://bastion.example.com"
  trusted_proxies: []          # see § The panel — required behind a proxy
  terminal_enabled: false      # browser terminal; opt-in, see § The panel

session:
  sftp: false
  idle_timeout: 30m
  max_lifetime: 12h
  accept_env: ["LANG", "LC_*"]

recording:
  dir: /var/lib/postern/recordings
  retain: 90d
  min_free: 5GB

target_probe:
  # Default false, and left false here on purpose: switching this on
  # makes postern run commands (uname, cat /etc/os-release) on every
  # target, and it logs a warning at every startup saying so.
  enabled: false
  refresh: 24h
  timeout: 5s

shutdown:
  # How long open sessions get to finish when postern is asked to stop.
  # When it expires they are closed with a reason, so the recording is
  # written and queued for the archive instead of being cut off.
  drain_timeout: 30s

sync:
  enabled: true
  interval: 1h
  grace: 24h
  dry_run: true

Relative paths resolve against the config file's own directory. accept_env is an allowlist: environment variables a user sends are dropped unless they match it.

Production checklist

  • TLS in front of the panel. Reverse proxy, or bind to localhost and tunnel.
  • trusted_proxies set to that proxy's address — otherwise the sign-in rate limit collapses onto the account and can be used to lock your administrator out.
  • CA key and secret key backed up, offline, and readable only by the service user. Neither is recoverable.
  • Database backed up, and its DSN not sitting in a world-readable file — use POSTERN_DATABASE_DSN.
  • A second break-glass administrator, its secret stored where the bastion being down does not block reaching it.
  • Sync run dry for a cycle before it is allowed to revoke anything.
  • Recording disk monitored — min_free makes a full disk refuse sessions, which is correct and still an outage.
  • A second way into new targets until you have proved certificate login works on each.
  • Decide record_input deliberately and tell the people it applies to.
  • Restrict who reaches the SSH port. postern is the door; it is not a firewall.
  • Practise the recovery: revoke your own admin role in a test install and get back in with the CLI. Find out now, not during an incident.

Rotating the CA

Rotation is additive — trust both keys, then drop the old one.

  1. postern ca init against a new path.
  2. Append the new public key to /etc/ssh/postern_ca.pub on every target (TrustedUserCAKeys accepts several).
  3. Point ca.key_file at the new key and restart. New sessions use it.
  4. Once no live session predates the switch, remove the old key from targets.
Never rotate by replacing

Swapping the key on the bastion before targets trust the new one locks everyone out of everything at the same moment.

Troubleshooting

"Permission denied (publickey)" from the target

postern authenticated you and the target rejected the certificate. Check on the target: is TrustedUserCAKeys pointing at the key postern ca show prints, and does auth_principals/<os_user> contain the principal? Then read journalctl -u ssh there — sshd says exactly which of the two failed.

A target shows no facts, or connecting to it fails

These are two different things and only one of them involves the probe. The panel has no "unreachable" state: it shows Last reached and, when target_probe is on, what the machine said about itself. Empty facts mean the probe is off or has not run — refresh defaults to 24 hours — not that the host is down, and target_probe.timeout bounds those identification commands only. A session never waits for the probe and is never refused by it.

If connecting fails, the answer is between the bastion and the target: try the dial by hand from the bastion host. A firewall in between is the usual cause; a changed host key is the other, and that one is reported rather than accepted.

"no route to host" only from some places

On macOS, a process needs Local Network permission to reach hosts on the LAN. A binary launched from a terminal that has not been granted it sees local addresses fail while WAN addresses work. Grant the terminal application the permission and run it again.

Signed in, but no targets

Their group arrived and nothing was mapped to it: postern mapping unmapped --config postern.yaml. If the group looks empty, check whether it is truncated rather than empty (§ Group mappings).

Discovery matched nothing

The command prints the tags it saw. Compare them to --tag-key; on Proxmox remember the value is in the same flat tag, separated by _.

The panel did not change after a rebuild

make web alone does nothing to a running server — the assets are embedded. Rebuild the binary.

Which version am I running?

Ask the binary, or read the first line the service logged when it started — postern writes its version before it even reads the config file, so it is there even for a start that failed: 

$ postern version
postern v1.0.0
  commit    3f2a9c1de4b0 (clean)
  committed 2026-09-03T10:12:44Z
  go        go1.26.6
  platform  linux/amd64

Two lines are worth reading closely. A build that did not come from a release tag says so rather than inventing a number, and a build made from a modified working tree is marked MODIFIED — the tag it carries does not then correspond to any commit, which is exactly the distinction that matters when you are checking whether a patch is actually in the binary you are running.

Someone was re-created in the directory and cannot sign in

A directory that deletes and re-creates a person gives them a new stable identity. postern binds accounts to that identity rather than to a username — deliberately, so renaming somebody does not hand their access to whoever takes the old name — so the account is now bound to an identity nobody has. Signing in through the browser answers this bastion has no account for you, and SSH refuses with not in the directory.

Detach the old binding on the bastion host. The next directory sign-in binds the account again, and roles, keys and session history are untouched: 

$ postern user unbind-directory --name ayse --config postern.yaml
"ayse" is bound to directory identity 9f2c…
detaching means the NEXT directory sign-in claims this account, whoever it comes from.

type the account name to confirm: ayse
Only when the directory really did re-create them

Between detaching and their next sign-in, the account is claimable by whatever directory identity signs in with that username. That is why the command lives on the host and not in the panel, and why it writes to the admin log: it is the one command that opens an existing account to a different identity. Confirm who you are helping before running it.

Locked out of the panel

Go to the host. postern admin issue --name <user> prints a fresh secret. This is why the local administrator is never removed.

Limits of 1.0

  • SSH and SFTP only. No HTTP, RDP, VNC, database or Kubernetes proxying.
  • Single node. No clustering or shared state. Recordings are local files; the archive copies finished ones to a bucket but does not make a second node possible.
  • TOTP only as a second factor — no WebAuthn, no push.
  • No port forwarding, by design.
  • No integrity seal on recordings. A recording is evidence of what happened, not proof it was not altered afterwards — no hash chain, no signature. Deliberate: anyone able to rewrite the files already owns the bastion, and a chain computed and stored on that same machine is one they can recompute. The archive's protection comes from the bucket instead (versioning, Object Lock), which is why archive check reports on it.
  • Closing a session reaches only this process. A second postern against the same database is not asked and cannot be told; the panel answers "not running on this instance" rather than pretending. That startup sweep would also close the other instance's live rows — one more reason 1.0 means one node.
  • The panel speaks HTTP; TLS is your reverse proxy's job.
  • Certificate login only on targets. postern does not carry a user's own key or a password through to a server that does not trust the CA.

1.0 means the paths above are built and tested against real OpenSSH, Keycloak, OpenLDAP and PostgreSQL on every change. It does not mean years of production behind it. Treat it as a careful new tool, and keep the second way in.
